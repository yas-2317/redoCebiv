## ADR-001: フレームワークに Next.js（App Router）を選ぶ

**日付**: 2026-03-18
**状態**: 採用

**背景**:
Web アプリとして構築する。対応スタックの主戦場が Next.js / React / TypeScript であり、ターゲットユーザーのコードも同スタックが多い。

**決定**:
Next.js（App Router）+ TypeScript + Tailwind CSS を採用。

**理由**:
- ターゲットユーザーが持つコードと同スタックで開発することで、トレース機能の実装が自然になる
- App Router は Server Component による初期表示最適化・ファイルベースルーティングが優れている
- Tailwind は shadcn/ui との相性が良い
- Vercel へのデプロイが容易

**代替案**:
- Remix: 良い選択肢だが、エコシステムが Next.js より小さい
- Vite + React SPA: シンプルだが、将来的な SSR 対応が面倒

## ADR-002: 初期入力をZIPアップロードに絞る

**日付**: 2026-03-18
**状態**: 採用

**背景**:
ユーザーのプロジェクトをどう読み込むか。

**決定**:
MVP は ZIP アップロードのみ対応。GitHub 連携は後回し。

**理由**:
- 認証・OAuth 実装が不要でMVPの速度を上げられる
- ターゲットユーザーは GitHub に不慣れな可能性が高い
- ZIP でもユーザー体験として成立する

**後続候補**:
- GitHub リポジトリ URL からの直接取得
- GitHub App による連携

## ADR-003: DBにSupabaseを採用する

**日付**: 2026-03-18
**状態**: 採用

**背景**:
成長トラッキング・プロジェクト保存・ユーザー管理にDB・Auth・Storageが必要。

**決定**:
Supabase（PostgreSQL + Auth + Storage）を採用する。

**理由**:
- Auth・DB・Storage・RLSが1サービスで完結し、MVP開発速度が最大化
- Free tier（DB 500MB / Storage 1GB / 50k MAU）でMVP規模は無償
- Pro $25/月はLite 7人で回収できる
- ZIPファイルはStorageに一時保存し、解析完了後即削除

**代替不採用理由**:
- Neon: Auth・Storageが別途必要でMVP速度が落ちる
- PlanetScale: MySQL系・Free廃止済み

## ADR-004: AIにClaude（Anthropic）全統一を採用する

**日付**: 2026-03-18
**状態**: 採用

**背景**:
コード理解と日本語説明の質がコア体験に直結する。複数プロバイダー管理のコストを避けたい。

**決定**:
全用途をAnthropicで統一し、用途別にモデルを使い分ける。

| 用途 | モデル | 理由 |
|---|---|---|
| 初期解析・機能トレース・変更候補 | claude-sonnet-4-6 | 200kコンテキスト・高品質推論 |
| 課題生成・採点・解説 | claude-haiku-4-5 | 短文生成でコスト削減 |

**200kコンテキストウィンドウが採用の決め手**:
- Next.jsプロジェクト全体 ≈ 25k tokens → 余裕を持って1コールで解析可能
- チャンク分割が不要になり、実装がシンプルになる

**トレースキャッシュ戦略**:
- トレース結果はDBに保存し、ZIPのSHA256ハッシュと紐付ける
- 同一ハッシュなら再生成せずDBから返す（コスト$0）
- 再アップロード時のみキャッシュ破棄・再生成

**ストリーミング方針**:
- 採用: 機能トレース説明・変更候補（長文・ユーザーが待つ）
- 不採用: 課題採点（全文が揃ってから表示が必要）

## ADR-005: クレジット制を採用する（月次リセット）

**日付**: 2026-03-18
**状態**: 採用

**背景**:
フリーユーザーの爆増によるAIコスト破綻を防ぐ必要がある。

**決定**:
月次リセット型クレジット制を採用する。

| プラン | 初回ウェルカム | 月次付与 | 月間上限コスト |
|---|---|---|---|
| Free | 15cr | 5cr/月 | ~$0.85（初月）/ ~$0.30（以降） |
| Lite | なし | 100cr/月 | ~$1.45 |

**クレジット消費レート**:
| アクション | 消費 | コスト相当 |
|---|---|---|
| 初期解析 | 5cr | $0.40 |
| トレース（初回生成） | 1cr | $0.07 |
| トレース（キャッシュ済み） | 0cr | $0 |
| 変更候補クエリ | 2cr | $0.04 |
| 課題採点 | 1cr | $0.015 |

**月次リセットを選んだ理由**:
- プロダクトのコアは「継続的な成長」→ 毎月使い続ける動機が必要
- ライフタイム制はクレジット温存で体験が浅くなるリスクがある

**全体キャップ**:
フリーティア全体の月間AIコスト上限$300。超過時は新規フリーユーザーのAIリクエストをキュー待ちに。

## ADR-006: バックグラウンド処理にInngestを採用する

**日付**: 2026-03-18
**状態**: 採用

**背景**:
ZIP解析→AI処理は30〜60秒かかる。Vercel Hobbyのタイムアウト10秒を超えるため非同期処理が必須。

**決定**:
Inngestを採用し、ZIPアップロード後の解析をバックグラウンドジョブとして実行する。

**理由**:
- 無料枠50k runs/月でMVP規模は無償
- Next.js App Routerとの統合が簡単（`/api/inngest` 1エンドポイントで完結）
- リトライ・ログ・エラーハンドリングが組み込み済み
- Vercel Pro不要（コスト節約）

**処理フロー**:
APIがZIPを受信 → Supabase Storageに保存 → Inngestジョブをトリガー → 202を返却 → バックグラウンドで解析 → DB更新

## ADR-007: 機能の単位をユースケース単位に確定する

**日付**: 2026-03-18
**状態**: 採用

**背景**:
機能トレースの「機能」を何の単位で定義するかがプロダクト全体の設計に影響する。

**決定**:
ユーザーの行動目標1つ（「タスクを追加する」「ログインする」）をユースケース単位とする。

**理由**:
- 画面単位は粒度が大きく複数機能が混在して説明しにくい
- ボタン単位は粒度が小さく処理フローの全体像が見えにくい
- ユースケース単位は初心者が「やりたいこと」と一致しやすい

## ADR-008: 認証にGoogle OAuth + メール/パスワード両方を採用する

**日付**: 2026-03-18
**状態**: 採用

**背景**:
非エンジニアターゲットに対して登録の摩擦を最小化したい。一方でGoogleアカウントを持たないユーザーもカバーする必要がある。

**決定**:
Supabase Auth で Google OAuth とメール/パスワードの両方を提供する。

**理由**:
- Google OAuth は1クリックで完了し、非エンジニアの離脱を最小化
- メール/パスワードはGoogleアカウントを持たないユーザーをカバー
- Supabase Auth は両方を標準でサポートし、実装コストが低い
- メール確認フローはSupabase + Resendで完結

**実装方針**:
- UIの優先順位: Googleボタンを上・目立つ位置、メールは下に配置
- メール登録時はSupabase標準の確認メール（Resend経由）を送信
- どちらの方法でも同一のprofileレコードを生成し、クレジット管理は共通化

## ADR-009: 多スタック対応では primary stack を明示解決する

**日付**: 2026-03-20
**状態**: 採用

**背景**:
対応スタックを Flutter / Swift / Rails / Python / Vue / Svelte 系へ広げる中で、1プロジェクト内で複数 stack が検出されるケースが発生する。file selection と prompt selection が別々の判断をすると、AI の読むファイルと説明文脈がずれる。

**決定**:
`getPrimaryStack(projectStack)` を導入し、file selection と prompt selection の両方が同じ primary stack を参照する。

**理由**:
- 複数 stack 混在時の挙動を暗黙ではなく明示できる
- `selectFilesForAnalysis()` と `getStackPromptContext()` の判断基準を揃えられる
- 新 stack 追加時の修正箇所が明確になる

**現行優先順位**:
- Flutter
- Swift
- Ruby on Rails
- Python
- Vue
- Nuxt
- Svelte
- SvelteKit
- Next.js
- React
- どれにも該当しない場合は `projectStack[0]`

## ADR-010: trace / proposal の AI 実行は service に集約し、失敗時は返金補償する

**日付**: 2026-03-20
**状態**: 採用

**背景**:
trace と proposal が route / page に分散していると、課金順序、保存失敗時の補償、AI 生成失敗時の返金がずれやすい。実際に、先行課金や返金漏れのリスクが発生していた。

**決定**:
trace / proposal の業務ロジックを service に集約し、`file確認 -> 課金 -> AI生成 -> 保存 -> 補償` の順序を統一する。

**理由**:
- correctness を 1 か所で担保できる
- route / page の責務を薄くできる
- 保存失敗や AI 失敗の返金補償を一貫して扱える

**補償方針**:
- AI 生成失敗: 返金する
- 保存失敗: 返金する
- trace の UNIQUE 制約違反: 返金後に既存 trace を返す

## ADR-011: challenge 採点は無料にする

**日付**: 2026-03-20
**状態**: 採用

**背景**:
challenge 採点は redoCebiv の継続利用と学習定着の中心導線であり、
ここに課金摩擦を置くと提出回数が減ってプロダクト価値が落ちやすい。

**決定**:
`challenge_grade` のクレジット消費は 0 とする。

**理由**:
- 課題提出の心理的ハードルを下げたい
- トレースや proposal に比べて 1 回あたりのコストが軽い
- 継続的な挑戦回数を増やすことが、プロダクト全体の定着に寄与する

## ADR-012: stack 別 progress は primary stack のみに帰属させる

**日付**: 2026-03-20
**状態**: 採用

**背景**:
複数 stack を含む project を stack 別 progress に重複計上すると、
合計値と内訳の整合が崩れやすい。

**決定**:
stack 別 progress 集計では、各 project を `getPrimaryStack(project.stack)` が返す
1 つの stack のみに帰属させる。

**理由**:
- 全体値との整合が取りやすい
- stack 別集計で重複カウントを避けられる
- 実装と説明がシンプルになる

## ADR-013: project_files のコンテンツ削除は「最終アクセスから30日」に変更する

**日付**: 2026-03-21
**状態**: 採用

**背景**:
当初 ADR-003 では ZIP を解析完了後即削除とし、project_files は作成から30日後に削除する方針だった。しかし「作成から30日」では、アクティブに使っているユーザーのファイルも削除される。削除後は新規トレース・変更候補生成が不可になるため、同じプロジェクトを再度使いたい場合に5crの再アップロードが必要になる。これはフリーユーザー（月3〜5cr）には実質的な利用制限になる。

**決定**:
project_files のコンテンツ削除タイミングを「作成から30日後」→「最終アクセスから30日後」に変更する。

- 削除条件: `projects.last_accessed_at < NOW() - INTERVAL '30 days'`
- `last_accessed_at` はトレース生成・変更候補生成・課題生成のたびに更新する
- ZIP は解析完了後即削除（ADR-003 変わらず）

**理由**:
- アクティブに使っているプロジェクトのファイルが消えない
- 放置プロジェクトのみ削除されるため、ストレージコストの削減効果は維持できる
- 5cr の再アップロード壁がフリーユーザーに発生しない

**影響**:
- `projects` テーブルに `last_accessed_at` カラムの追加が必要
- Inngest cron job の削除条件を `created_at` → `last_accessed_at` に変更
