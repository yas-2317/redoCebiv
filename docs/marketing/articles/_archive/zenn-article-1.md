## 本文

### はじめに

Cursorで作ったアプリが動いた。最高だ。

でも翌日、「ボタンのテキストを変えたい」と思って開いたら、ファイルが20個ある。どれを見ればいいか分からない。怖くて触れない。

これ、あなたのせいじゃないです。

vibe coding（AIに作らせる開発スタイル）には「理解のプロセス」が抜けているという構造的な問題があります。

この記事では、AI生成コードを「機能から逆向きに読む」方法を紹介します。

---

### vibe codingで起きていること

AIに作らせると、コードは正しく動きます。でも、あなたはそれを書いていない。

結果として：

- どのファイルが何をしているか分からない
- どこを変えると何が壊れるか分からない
- 「理解している」という実感がない

これは「コードが難しすぎる」のではなく、「理解の入り口が間違っている」だけです。

---

### 機能起点で読む

従来の「コードの読み方」は、ファイルを上から読む方法です。

でも、AI生成コードには向いていません。ファイル数が多く、どこが入口か分からないからです。

**機能起点の読み方**は逆です。

> 「タスクを追加するボタン」を押すと、何が起きるか？

この問いから追いかけます。

---

### 具体的なステップ

**Step 1: ボタンの `onClick` を探す**

```tsx
// AddTaskForm.tsx
<button onClick={handleSubmit}>追加</button>
```

`handleSubmit` という関数が呼ばれていることが分かる。

**Step 2: その関数の定義に飛ぶ**

```tsx
const handleSubmit = () => {
  if (text.trim() === '') return;
  addTask(text);
  setText('');
};
```

- バリデーション（空チェック）
- `addTask` という別の関数を呼んでいる
- テキストをリセットしている

**Step 3: `addTask` がどこから来ているかを確認**

```tsx
const { addTask } = useTaskStore();
```

`useTaskStore` というhooksから来ている。これがデータ管理の場所だ。

---

### これだけで何が変わるか

この3ステップを繰り返すと、こういう理解が積み上がります：

- 「このボタンを変えたいなら `AddTaskForm.tsx` を見ればいい」
- 「タスクのデータは `useTaskStore.ts` に入っている」
- 「バリデーションを追加したいなら `handleSubmit` の中を変える」

「どこを変えればいいか分からない」が、「ここを変えればいい」に変わります。

---

### 一番よくある「詰まりポイント」

**「関数が多くてどこを見ればいいか分からない」**

→ `onClick` / `onSubmit` / `onChange` など、ユーザーの操作に紐づくイベントハンドラーを探す。これが機能の「入口」です。

**「ファイルが多すぎて追えない」**

→ 関係するファイルは、最初は3〜4個です。全部読もうとしない。「この機能に関係するファイルだけ」を抽出することが重要。

**「どこまで読めば分かったことになるか分からない」**

→ 「変更したい場所のファイルと行番号が分かる」状態を目標にする。コード全体を理解する必要はありません。

---

### 理解の3段階

vibe codingからの理解には、3つの段階があります。

1. **読める** — 関連ファイルと処理の流れが分かる
2. **当てられる** — 「ここを変えればいい」が予想できる
3. **直せる** — 実際に変更を加えられる

多くの人は「読める」に至る前に「分からない」と諦めます。でも「読める」だけで、次の変更の怖さは劇的に減ります。
